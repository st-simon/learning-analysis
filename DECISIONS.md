# Decisions
- Hybrid: local Jina extraction, ChatGPT analysis; no Google OAuth flow.
- FastMCP stdio avoids another HTTP listener; tunnel-client forwards to the local process.
- Narrow exact host allowlist, public DNS check, 4 MB response cap, no automatic retries, private content-addressed archive.
- The host allowlist is a staged product-security policy, not a claim about all technically readable sites. Add domains only when there is a concrete need; evaluate each domain independently for security, privacy, reliability, extraction quality, and operational cost; allow the smallest necessary scope; and verify it before inclusion.
- 2026-09-14: source accessibility is Gate 0. Cloudflare + Jina SaaS is superseded as the main WeChat fetch route after a real article returned environment verification despite successful OAuth/MCP and a configured Jina key.
- 2026-09-16: Gate 0 prioritizes automatic extraction from an already rendered Chrome DOM through local MCP and Platform tunnel. Manual copy, paste, print or upload of article content is not an accepted fallback. Browser credentials, cookies, proxy controls and provider selection stay outside the public tool interface.
- 2026-09-16: Reader direct fetch is an optional fast-path probe, not an L3 blocker. First identify the SSH-forwarded backend without an article call; test one article and expand to two more only if the first succeeds.
- 2026-09-16: H3 uses Platform tunnel only. The existing Cloudflare Worker is frozen at zero Gate 0 requests as validation evidence. Disabling it or revoking GitHub/Jina credentials requires a separate explicit operation.
- 2026-09-16: Gate 0 passed the browser-first L3 feasibility threshold: 3/3 real articles and App/Web real-article transport passed. Reader direct fetch stopped before Jina because Mac TUN/Fake-IP DNS returned a non-public synthetic address. The probe is inconclusive—not evidence that Reader or WeChat failed—and is deferred outside the current L3 source/fallback selection.
- 2026-09-16: Full implementation is not yet approved. Gate 1 is split: Gate 1A verifies a minimum same-call wait window and exact extension pairing; only after a mandatory review may Gate 1B test per-user background lifecycle, supervised tunnel recovery, and clean uninstall.
- 2026-09-18: Disposable Gate 1B passed. A user-domain LaunchAgent started the tunnel/MCP path without root or secret-bearing plist data, recovered once from PID 24681 to 25377, served fixed App probes through both expected instances, and left zero runtime residue after uninstall. This does not authorize production installation or prove capture-bridge persistence or natural login/restart startup.
- 2026-09-20: Approved L3 implementation uses one user LaunchAgent for tunnel-client and stdio MCP. The MCP process directly owns `CaptureRuntime`; Chrome alone uses the authenticated loopback `/pending` and `/capture` adapter. The prior MCP-to-loopback GET path and separate bridge lifecycle are removed. Formal runtime assets live under private, ignored `runtime/learning-analysis`; F0-F2 passed, while App/Web articles, natural login, upgrade/uninstall, and final installation remain gated by F3-F6.
